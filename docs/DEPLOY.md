# Deploying the public demo

The demo runs on free tiers (ADR-0035): the web application on Vercel, the API on Render, its
database on Neon, and the language model on Groq. This is the runbook: what to create, in which
order, and what to type where. Every secret is typed by the account's owner into the platform
that keeps it, and never into the repository, a chat or a log.

| Part | Where | Plan | Built from |
| --- | --- | --- | --- |
| Web application | Vercel | Hobby | `apps/web`, on every push to `main` that changes it |
| API | Render, Frankfurt | Free | `apps/api/Dockerfile` (`render.yaml`), once CI has passed |
| Database | Neon, Frankfurt | Free | migrated by the API when it starts |
| Language model | Groq | Free | the account's key |

Redis (Upstash) is not needed: the API runs its jobs in its own process (`SEF_JOBS=inline`), and
the free plan runs one instance.

## 1. The database (Neon)

1. Create a project: Postgres 16, region **AWS Europe Central 1 (Frankfurt)**, where the API runs.
2. Open **Connect**, switch **Connection pooling** off, and copy the connection string. The direct
   connection is the one the API's driver, asyncpg, works with; a pooled one, whose host ends in
   `-pooler`, would break its prepared statements.
3. Rewrite it for the API, which requires the asyncpg driver and takes TLS as `ssl`. In a text
   editor, three edits: the scheme becomes `postgresql+asyncpg://`; `-pooler` goes from the host,
   if it is there; and everything from `?` becomes `?ssl=require`:

   ```text
   from: postgresql://USER:PASSWORD@ep-NAME-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require&channel_binding=require
   to:   postgresql+asyncpg://USER:PASSWORD@ep-NAME.eu-central-1.aws.neon.tech/neondb?ssl=require
   ```

   This is `DATABASE_URL`. Keep it in a password manager; it goes into Render, and into your own
   terminal for step 3, never into a chat or a screenshot.

`pgvector` and `pg_trgm`, which the corpus needs, are created by the migrations.

## 2. The API (Render)

1. **New > Blueprint**, and choose this repository. If Render lists no repository, connect it to
   GitHub (**GitHub: Connect account**); if this one is not listed, **Configure account** gives
   Render's GitHub app access to it. Render reads `render.yaml`: one web service,
   `sef-kopilot-api`, built from `apps/api/Dockerfile` on the free plan in Frankfurt, with
   `/ready` as its health check.
2. Render asks for the values the Blueprint does not hold:
   - `DATABASE_URL`: the URL of step 1;
   - `GROQ_API_KEY`: the key from <https://console.groq.com/keys>;
   - `SEF_WEB_ORIGINS`: the web application's address, `https://NAME.vercel.app`, without a
     slash. Before step 4 you do not know it yet: enter `https://sef-kopilot.vercel.app` and
     change it afterwards if Vercel gives another.

   `SEF_JWT_SECRET` is generated by Render. `LLM_PROVIDER=groq`, `FORWARDED_ALLOW_IPS=*` and
   `SEF_PUBLIC_DEMO=true`, with which the upload asks for synthetic invoices only, come from the
   Blueprint.
3. Apply. The first build takes several minutes: the image fetches and compiles the rule sets.
   When the deploy is live, `https://sef-kopilot-api.onrender.com/ready` (the name Render gave the
   service) answers `{"status":"ready",...}`, and `/docs` shows the API.

A deploy then follows every push to `main` whose checks pass and which changes what the image is
built from (`buildFilter` in `render.yaml`). A free service sleeps after 15 minutes without a
request; the next one wakes it, which takes about a minute, while the pages say that the API is
waking up and wait for it (ADR-0036).

## 3. The corpus (once, from your machine)

The explanations cite the official documents of `corpus/`, which the database must hold. A free
service has no shell, so load them from a clone, after the API's first deploy has migrated the
database:

```powershell
$s = Read-Host "DATABASE_URL" -AsSecureString
$env:DATABASE_URL = [pscredential]::new('x', $s).GetNetworkCredential().Password
uv run python -m sef_api.rag.ingest
Remove-Item Env:DATABASE_URL
```

Paste the URL when it asks: it is shown as asterisks, and kept out of the shell's history and
of the screen. The ingest prints how many documents and passages it added, changed or kept. It
can run any number of times; run it again when `corpus/` changes.

## 4. The web application (Vercel)

1. **Add New > Project**, and import this repository. If Vercel does not list it, its GitHub app
   has access to some repositories only: **Adjust GitHub App Permissions** (or GitHub >
   **Settings > Applications > Vercel > Configure**) and add this one. GitHub first asks for a
   code it sends by e-mail.
2. **Root Directory**: `apps/web`. The framework, Next.js, is detected; `vercel.json` skips a
   build when a commit changes nothing of the web application, and `package.json` asks for
   Node.js 22, which decides over the project's own setting, a newer version by default.
3. **Environment Variables**, for every environment:
   - `NEXT_PUBLIC_API_URL`: the API's address from step 2, `https://sef-kopilot-api.onrender.com`;
   - `ENABLE_EXPERIMENTAL_COREPACK`: `1`, so that the build uses the pnpm version that
     `package.json` names.
4. Deploy. The production address is the one the API's `SEF_WEB_ORIGINS` must name: if it is not
   the one entered in step 2, change the variable in Render (**Environment**), which redeploys.

`NEXT_PUBLIC_API_URL` is written into the code the browser loads when the application is built:
after changing it, redeploy. On Vercel, Next.js knows the site's own address, which the image a
shared link shows needs whole; a build elsewhere reads it from `SITE_URL`.

Preview deployments have addresses of their own, which the API does not allow, so their pages
cannot call it; Vercel's own sign-in protects them, as it does each deployment's own address
(the team's default Deployment Protection). The production domain stays public.

## 5. Check it

1. Open the web application. The footer says whether the API answers; after a sleep, the first
   visit wakes it, and the page says that it is waking up until it answers.
2. Register, upload a synthetic invoice from `fixtures/invoices/synthetic/` (never a real one:
   the demo is public), read its report, ask for an explanation and for a repair, approve it.
3. `https://sef-kopilot-api.onrender.com/ready` answers `ready`, with the database and the
   validator `ok`.
4. Ask for the explanations: each cites passages of the corpus. If every rule comes back
   unexplained ("This rule was not explained this time"), the corpus is missing: run step 3
   against this database.

## 6. Connect an assistant (OAuth 2.1)

The MCP endpoint, `https://sef-kopilot-api.onrender.com/mcp`, takes an API key from any client.
An assistant that signs its user in, such as Claude's or ChatGPT's connectors, needs the API's
authorization server (ADR-0044), which is off until the API knows its own address:

1. Render > the API > **Environment**, three variables, which redeploy the service:
   - `SEF_PUBLIC_URL`: `https://sef-kopilot-api.onrender.com`, the API's address, without a
     slash.
   - `SEF_WEB_URL`: `https://sef-kopilot.vercel.app`, the web application's address, which must
     be one of `SEF_WEB_ORIGINS`: its page is where a person decides what an assistant may do.
   - `SEF_CLIENT_METADATA_DOCUMENTS`: `true`, for assistants that introduce themselves by a
     metadata document instead of registering (ADR-0045); the others register either way.
2. Check: `https://sef-kopilot-api.onrender.com/.well-known/oauth-authorization-server`
   answers with the server's endpoints.
3. In the assistant, add a connector with the address `https://sef-kopilot-api.onrender.com/mcp`.
   It registers itself, sends you to the web application to sign in and allow it, and lists the
   tools. Ask it to validate one of the synthetic invoices.

Nothing else is configured: there is no client to register by hand and no secret to keep, since
every client is public and proves itself with PKCE.

## Rolling back

- The API: Render > the service > **Events**, and **Rollback** to an earlier deploy. A migration
  is undone from a clone with `uv run alembic -c apps/api/alembic.ini downgrade -1`, with
  `DATABASE_URL` set as in step 3.
- The web application: Vercel > **Deployments**, and **Promote** an earlier one.

## Limits of the free plans

- Render: 750 instance hours a month, shared by every free service of the workspace; a sleeping
  service uses none. 512 MB of memory, which the API's image fits with room (ADR-0034).
- Neon: 1 GB of storage and 100 compute hours a month per project; the compute suspends after
  5 minutes without a query and wakes on the next.
- Vercel Hobby: personal, non-commercial projects; 100 GB of data transfer and a million function
  invocations a month.
- Groq: the free tier's limits on requests and tokens a minute; the API's own limits are lower
  (`SEF_EXPLANATIONS_PER_MINUTE`).
