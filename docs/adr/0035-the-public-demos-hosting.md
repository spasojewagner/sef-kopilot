# 35. The public demo: the web application on Vercel, the API on Render, its database on Neon

- Status: accepted
- Date: 2026-11-07
- Deciders: Marko Spasojević
- Technical story: milestone M3, branch `chore/infra-deploy`; the questions ADR-0026 and ADR-0028
  left to it

## Context and problem statement

M3 ends with a public demo, on free tiers only. The brief names Render, Neon, Upstash and
Cloudflare Pages. Two questions were left open: whether the web application is a static export
or runs on a Node.js server, which the report's page needs to read an invoice's id from its
address (ADR-0028), and how preview deployments reach the API (ADR-0026). Where does each part
run, and what does it cost to keep it free?

## Decision drivers

- Free, and within each plan's limits, for a demo with a handful of visitors at a time.
- The web application as it is built, with no change to its pages: a server for the report's
  page, the static shell of every page around it (ADR-0028).
- The API's image as it is (ADR-0034), on 512 MB.
- Every secret kept by the platform that uses it.
- Deploys that follow `main`, and only commits whose checks passed.

## Considered options

The web application:

1. **Vercel, Hobby plan.** Chosen.
2. Cloudflare, with the OpenNext adapter on Workers.
3. A static export on Cloudflare Pages.

The API: **Render's free web service, from the Dockerfile**, chosen; or a container platform with
more memory, which none offers free.

The queue: **none, the jobs in the API's process**, chosen; or Upstash's Redis.

## Decision outcome

**The web application runs on Vercel's Hobby plan**, built from `apps/web` with Node.js 22 and
the pnpm version `package.json` names (Corepack). Vercel runs Next.js as it is: the static shells
are served from its network, and the report's page reads its id on request. A commit that changes
nothing of the web application is not built (`vercel.json`). This departs from the brief's
Cloudflare Pages: there, the report's page would need the OpenNext adapter, whose Worker the free
plan limits to 3 MiB compressed, or a static export that reads the id in the browser behind a rule
of the host. The Hobby plan is for personal, non-commercial projects: a commercial launch moves to
Vercel's Pro plan or to Cloudflare's paid one.

**The API runs on Render's free web service**, from `render.yaml`: the image of ADR-0034 in
Frankfurt, `/ready` as its health check, deployed from `main` once CI has passed on the commit
(`autoDeployTrigger: checksPass`) and only when the commit changes what the image is built from.
`SEF_JWT_SECRET` is generated by Render; the database's URL, the model's key and the web
application's origin are typed in when the Blueprint is applied. `FORWARDED_ALLOW_IPS=*`, since
Render's proxy is the only way to the container.

**The database is Neon's free plan** in the same region, through its direct connection
(`postgresql+asyncpg://...?ssl=require`), not the pooled one, which would break asyncpg's prepared
statements. The API's start migrates it. The corpus is loaded once from a developer's machine,
since a free service has no shell and no one-off jobs.

**No queue.** The API runs its jobs in its own process, as a deployment of one process does
(ADR-0019); the free plan runs one instance. Upstash is not needed until there are workers.

**Preview deployments** of the web application have addresses of their own, which the API does
not allow (`SEF_WEB_ORIGINS` names the production one), so their pages cannot call it; Vercel's
sign-in protects them. Allowing them is a change of the API's CORS for when previews need it.

`docs/DEPLOY.md` is the runbook.

### Consequences

Good:

- No change to the web application, and the report's page works as it was built.
- Nothing paid, and no secret in the repository.
- A deploy of the API waits for CI, and neither part rebuilds for a commit that changes only the
  other.

Bad / accepted:

- A sleeping API: Render's free service sleeps after 15 minutes without a request and takes about
  a minute to wake, with the image's own start of about 35 s on a small CPU. The pages must say
  that the API is waking up rather than that it fails: the next branch.
- Render's 750 free hours a month are shared by every free service of the workspace.
- Neon's compute suspends after 5 minutes; the first query after it waits a moment.
- A public demo sends what is uploaded to Groq when explanations or repairs are asked for: only
  synthetic invoices belong there, and the pages should say so.
- Two platforms' dashboards, and the web application's origin typed into the API's settings.

## Pros and cons of the options

### Cloudflare, with the OpenNext adapter

- Good: generous free traffic, and the brief's choice.
- Bad: the server's code runs as a Worker, which the free plan limits to 3 MiB compressed; a
  Next.js application with its dependencies is near or above it, and the paid plan is the fix.
  An adapter between Next.js and the platform is one more thing to keep in step with both.

### A static export on Cloudflare Pages

- Good: static files only, free and fast.
- Bad: no server for the report's page, which would read the id in the browser, behind a
  rewrite of the host (ADR-0028); the language redirect of `proxy.ts` would move to the host too
  (ADR-0026).

### Upstash's Redis

- Good: workers could run beside the API, and the jobs survive its restarts in the queue.
- Bad: no workers to run on a free plan, and one more account and secret for nothing yet.
