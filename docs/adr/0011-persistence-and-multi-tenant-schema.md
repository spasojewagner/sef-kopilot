# 11. Persistence: PostgreSQL through async SQLAlchemy, Alembic migrations, a schema keyed by organization

- Status: accepted
- Date: 2026-11-04
- Deciders: Marko Spasojević
- Technical story: milestone M2, branch `feat/api-settings-database`

## Context and problem statement

From M2 on the API keeps state: organizations, their members and roles, and later invoices,
jobs, regulation chunks and audit logs. The brief fixes PostgreSQL 16 with pgvector, SQLAlchemy
2 async with asyncpg and Alembic, and asks that every tenant table carry `organization_id` and
that row-level access be enforced in the service layer and tested. Still open: how configuration
reaches the application; how the engine and the sessions live; how migrations are written, run
and shown to be reversible (the definition of done asks for `alembic downgrade -1` in CI); the
conventions of the schema; what "every table" means for a person who works for several
organizations; and how tests get a real database.

## Decision drivers

- One source of truth for the schema, reviewed as code and reversible step by step.
- Tests on the database the product runs on: constraints, cascades, transactional DDL, and later
  pgvector and `pg_trgm`, behave differently or do not exist elsewhere.
- Tenant isolation a reviewer can check: one rule, applied everywhere, with tests that try to
  break it.
- No credential in a log line, an error message or a `repr`.
- The same code on a laptop (Docker), in CI (a service container) and on Neon.

## Considered options

1. **pydantic-settings; one async engine per application and one session per request, with
   explicit commits; Alembic migrations inside the package, with sequential ids, a naming
   convention and an exact downgrade each, and tests that prove both directions and that the
   models and the migrations agree; tenant tables keyed by `organization_id`, people global with
   memberships; tests on a real PostgreSQL, in a database of their own** — chosen.
2. SQLite, or an in-memory fake, in the tests.
3. `Base.metadata.create_all()` instead of migrations.
4. A user account per organization.
5. PostgreSQL row-level security from the start.

## Decision outcome

Option 1. Concretely:

- **Settings.** `Settings` (pydantic-settings) reads the variables of `.env.example` from the
  environment or a `.env` file, and is frozen. `DATABASE_URL` is a `SecretStr`, must use
  `postgresql+asyncpg://`, defaults to the database of `make up` and is required in production;
  validation errors never echo a value.
- **Engine and sessions.** `create_app(settings)` creates the `Database`: an engine with
  `pool_pre_ping` (Neon closes idle connections) and a session factory with
  `expire_on_commit=False`. Nothing connects before the first query; the lifespan disposes of the
  engine. `get_session` gives each request its own session, and services commit explicitly
  where their unit of work ends. `GET /ready` runs `SELECT 1` within two seconds and answers 503
  when it cannot.
- **Migrations.** Alembic, with the scripts in `sef_api/migrations` so that they ship with the
  package (`script_location = sef_api:migrations`); run them with
  `alembic -c apps/api/alembic.ini` or, from code, with `alembic_config(url)`. Revision ids are
  `0001`, `0002`, …, every constraint and index is named by a convention, an autogenerated script
  is a draft that is reviewed and given an exact downgrade, and a migration that has run is never
  edited. The tests apply every migration to an empty database and run `alembic check` (models
  and migrations describe the same schema), undo them all and apply them again, and undo each
  step on its own; CI also runs the command line: upgrade, downgrade -1, upgrade.
- **Schema conventions.** UUID keys, generated by `gen_random_uuid()` in the database and by
  `uuid4` in Python, so that neither side depends on the other; `timestamptz` throughout;
  enumerations as `VARCHAR` with a CHECK constraint, because adding a value is then a one-line
  migration, unlike `ALTER TYPE` on a native enum; e-mail addresses stored in lower case, enforced
  by a CHECK.
- **Tenancy.** An organization is the tenant. Every table that holds a tenant's data has
  `organization_id NOT NULL`, a foreign key with `ON DELETE CASCADE`, and an index that begins
  with it. People are global — one account per e-mail address — and belong to organizations
  through `memberships (organization_id, user_id, role)` with the roles `owner`, `accountant` and
  `client`. Queries on tenant tables go through the service layer, which always filters by the
  caller's organization; every endpoint that reads or writes tenant data gets a test in which a
  member of another organization makes the same request. The first such endpoints arrive with the
  RBAC branch.
- **Tests.** `SEF_TEST_DATABASE_URL` names a server. The suite creates `sef_test_<random>` there,
  migrates it, runs each test in a transaction that it rolls back (savepoints let code under
  test commit) and drops the database at the end. Without the variable the database tests are
  skipped; CI provides PostgreSQL 16 with pgvector as a service.

### Consequences

Good:

- The schema has one reviewed history that can be replayed and undone on any database.
- Tests catch what only PostgreSQL enforces: constraint names, cascades, unique e-mails, roles.
- An accountant uses one account for every organization they work for; isolation is still a
  single rule.

Bad / accepted:

- Running the database tests locally needs Docker or a PostgreSQL server.
- Coverage of the API is measured by path, because Alembic runs `env.py` and the revisions as
  standalone modules that a package name does not match.
- Service-layer scoping depends on every query going through it; the cross-tenant tests are the
  guard, and row-level security remains available as a second line.

## Pros and cons of the options

### SQLite or a fake in the tests

- Good: fast, no server.
- Bad: no pgvector or `pg_trgm`, different CHECK, cascade and DDL semantics, no
  `gen_random_uuid()`, timestamps without time zones — tests that pass where production fails.

### `create_all()` instead of migrations

- Bad: no history and no way back; a database that holds data cannot be brought to a new schema.

### An account per organization

- Good: isolation by construction.
- Bad: an accountant serving ten companies would need ten accounts and ten passwords; the roles
  in the brief describe people who work across organizations.

### Row-level security now

- Good: isolation enforced by the database itself.
- Bad: with a connection pool every transaction must set the tenant (`SET LOCAL`), and migrations
  and maintenance jobs must set or bypass it; with memberships as the only tenant data there is
  nothing yet to protect. To be reconsidered as a second line when invoices are stored.
